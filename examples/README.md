# Executed sample outputs

The three text reports are unedited investigation outputs produced against the seeded DataHub
catalog through the DataHub MCP Server:

| Report | Incident | Root cause found |
|---|---|---|
| [`A_partial_load.txt`](A_partial_load.txt) | Revenue dropped about 40% | `prod.raw.orders`: silent partial load |
| [`B_schema_drift.txt`](B_schema_drift.txt) | Customer emails went blank | `prod.raw.customers`: `email` renamed to `email_address` |
| [`C_stale_feed.txt`](C_stale_feed.txt) | USD revenue froze | `prod.ref.exchange_rates`: feed six days stale |

The [`generated`](generated/) directory continues each incident into the current repair workflow.
Every case contains:

- the exact proposed SQL and unified diff;
- the hash-bound sandbox receipt;
- a ZIP handoff packet;
- proof that the incident-specific assertion passed and cleanup/rollback was verified.

[`generated/manifest.json`](generated/manifest.json) records every artifact size and SHA-256. It
is regenerated by running:

```bash
python tools/generate_release_examples.py
```

These examples prove the bundled cases. They are not a claim that every customer incident has the
same repair; the product also accepts an arbitrary DataHub asset, symptom, and checked-out dbt SQL
file, then constrains the proposal to the evidence and existing relation scope.
